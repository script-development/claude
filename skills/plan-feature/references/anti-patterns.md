# Anti-patterns to avoid

Lessons-from-pain captured outside SKILL.md so they're loaded once on demand, not every invocation. Mechanics that SKILL.md already states as rules (how to use `AskUserQuestion`, how short to keep inter-round text, pushing back on vague answers) are not repeated here — this file is for the failures those rules don't describe.

- **Skipping the Kendo board check** — issues and epics may already define the scope
- **Skipping the shared code audit** — don't plan to build what already exists in the project's shared layer
- **Writing "add tests" without behavioral detail** — every test in the plan must describe a user-visible outcome, not an implementation check. Read the project's stack-specific testing skills to understand the testing philosophy before writing test requirements
- **Generic questions** that could apply to any product — ground every question in the codebase
- **Asking about low-level implementation details** — "Should we use a computed property or a watcher?" — that's the developer's call during implementation
- **Self-reviewing your own conventions usage** — you will rationalize your choices. The Plan Reviewer agent exists specifically to catch what you won't. Never skip Phase 5.
- **Presenting your recommendation as settled** — the interview mode is "I'd pick X because Y — agree, or pick another?", not "we're using X, right?". A stance the developer can't cheaply reject is worse than no stance. (This supersedes the older "never ask leading questions" guidance: leading *with* a recommendation is now the required mode — what's forbidden is foreclosing the alternative.)
- **Designing from first principles instead of from the codebase** — if the codebase uses int-backed enums, your plan uses int-backed enums. If the codebase puts auth logic in a specific class shape, your plan puts auth logic in that shape. You don't get to invent a "better" approach unless the developer explicitly asks for a deviation. Plans built from first principles are the most expensive failure mode — one early plan proposed string enums and a PermissionService when the codebase used int-backed enums and Interaction classes, and cost a full restart when the deviation was caught at review.
- **Burying design decisions in the plan body** — the developer should not have to read 400 lines to find that you chose `category (string)` over `resource (tinyInteger)`. Key Design Decisions go in the table at the top. If a structural choice isn't in that table, it's invisible to review.

## Calibration: the fractional-rank plan (2026-05) — confidently-wrong claims cost three reviewer rounds

A plan for fractional-rank board ordering needed R1 → R2 → R3 reviewer cycles to converge. Each round caught a different category of confidently-wrong-but-unverified claim. The plan logic was structurally sound from R1 — the bullshit was at the citation layer. Phase 1.4 ("Pre-flight verification") was added in response to this calibration. Only the first two buckets below are resolved mechanically by `scripts/verify-citations.sh` — it answers "does this exist", which is all those two needed. The third needs a hand-written vendor `file:line`. The fourth needs the full grep-and-inspect pass and no script can shortcut it: knowing a symbol exists says nothing about whether you found all of its callsites, and callsite coverage is the entire bucket.

- **Phantom paths.** Wrote `app/Support/Rank.php` — `app/Support/` did not exist. The sibling helpers lived in `app/Helpers/`. Wrote `App\Broadcasting\Events\IssuePositionEvent` — that namespace didn't exist; events all lived at `App\Events\`. Both citations would have been one `ls` away. **Lesson:** if you say "the closest analog is X siblings", `ls` the directory holding the siblings first.

- **Fabricated route precedent.** Cited `POST /api/projects/{project}/issues/{issue}/start-work` as the per-issue route binding precedent. The Action behind it existed; no `start-work` route existed in `api.php`. The actual per-issue routes were `PUT {issue}` and `PUT {issue}/assignee` at `api.php:233-234`, and they DID use scoped `['issue', 'project']` binding — so the *convention claim* was right; the *precedent citation* was fabricated. **Lesson:** "this follows the X precedent" requires grep-confirming X exists. The convention may be real and the named example may still be invented.

- **Wrong framework behavioural claim.** Wrote "the `, 3);` retry budget on `$db->transaction(...)` covers `UniqueConstraintViolationException`." Verified false by `surface-reviewer` in R2 against `vendor/laravel/framework/src/Illuminate/Database/Concerns/ManagesTransactions.php:93,109` + `DetectsConcurrencyErrors.php`: the framework only retries on `causedByConcurrencyError()`, which matches SQLSTATE 40001 + a 10-string deadlock/lock-wait list. `1062 Duplicate entry` is NOT in the list. The mechanism the entire concurrency-recovery story depended on did not exist. **Lesson:** any claim of the form "the framework does X" / "the SDK does Y" needs a vendor file:line citation or an explicit downgrade to "verify at implementation." Reading two lines of framework source is cheaper than a R2 BLOCKER.

- **Removal-blast-radius miss.** Planned to delete a board-update endpoint based on two callsites (the board page and the backlog page's drag handler). A third callsite in the backlog page's bulk-epic-assign flow — selects N issues, posts the same payload shape to set `epic_id` on all of them — was a non-drag consumer of the same endpoint. The plan as written would not have compiled in PR1. **Lesson:** before scoping out the deletion of any symbol, `grep -r <symbol>` across every source tree and inspect *every* hit — not just the ones from the obvious feature path. The third callsite always lives somewhere unexpected.

The combined cost: three reviewer rounds, ~400 LOC of rewritten DECISIONS.md/PLAN.md, two BLOCKERs, and ~25 minutes of agent runtime. The combined cost of running Phase 1.4 up-front: under 10 minutes of grep. Confident-sounding planning needs grep-verified foundations — the same lesson as verifying SDK claims before encoding them, and verifying a spec against the data model before building on it.
